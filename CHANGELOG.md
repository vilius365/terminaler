# Changelog

## 2026-08-26

### Added
- **A notification kill switch in the sidebar dock.** The dock gains a fourth chip (`⊘`) that silences Terminaler outright: OSC 9/777 toasts, the Claude idle toasts, the Slack webhook, and the rail's own notification flash and count. It complements the existing per-pane mute, which only ever covered one pane. State is session-only, matching that per-pane mute — a config write would need a reload round-trip, and the switch exists to silence the next hour, not the next launch. The block folds into the same `is_muted` test the per-pane mute already uses rather than short-circuiting the Claude scan: returning early there would skip the `claude_prev_status` update, so a `WaitingInput` transition occurring during a block would fire the moment it was lifted. Verified against a working control rather than by reading code — identical OSC sequences reach the decision point with `is_muted=false` (toast fires) unblocked and `is_muted=true` (suppressed) blocked. Chip padding is now budgeted from the rail width instead of fixed, because the box model has no wrapping and an overflowing row silently clips its last chip: measured at the 100px minimum rail width with tmux sync enabled, four chips at the old fixed padding ran to x=107.5 against a 90px content edge and would have swallowed the new button outright. With the budget it ends at 85.4, and padding relaxes back to the original 9px once the rail is wide enough.

### Fixed
- **The pane toast toolbar vanished when you reached for it, and ctrl+right-click pasted under tmux.** Three defects behind "the layout controls are hard to use". The toast is painted against the pane's *visual* bounds — window padding, border and the sidebar offset included — but `hovered_pane_id` was re-derived on every mouse move from `pane_id_at_pixel_coords`, which tests only the **content** rect. Those rects are not the same: on a right-flush pane `bg_right` is `effective_right_edge()`, and at cell heights above 20px the toast also overhangs upward into the pane above (`bg_y = pane_top - cell_h/2`, toast at `+10`). Pointing at the toast therefore resolved to *no pane*, and the reset at that site ran with **zero margin**, clearing both the hover and the expansion before the 8px collapse margin was ever consulted. Because paint is gated on `hovered_pane_id`, the whole toast disappeared — collapsed pill included — rather than merely collapsing, and `toast_button_at` (also gated on it) stopped responding in the same frame. The keep-open test is now geometric, mirroring `de1a69e` for the sidebar flyout: the painted rect is stored each frame and the pointer counts as on the pane while inside it plus the margin. The hand-recomputed collapse geometry was **deleted** rather than corrected, which removed two latent bugs it carried — a missing `sidebar_x_offset()` (dormant only because the sidebar defaults to the right, so it would have struck the first user to move it left) and a keep-zone 2px shorter than the toast it guarded. Expanding widens the stored rect immediately, since it otherwise still describes the narrow pill until the next paint and a move arriving in that gap would collapse the toolbar as it opened. Separately, ctrl+right-click opened the overlay *after* `mouse_event_terminal` had already forwarded the press. No binding matches ctrl+right at all — the PuTTY-style paste requires `Modifiers::NONE`, the SHIFT bypass leaves CTRL intact, no default uses `mouse_reporting: true`, and `lookup_mouse` is an exact hash hit with no fallback — so under tmux with `mouse on` the raw SGR report reached tmux, which pasted on its own. Plain shells never grabbed the mouse and so never pasted, which is why only tmux misbehaved; the symptom was tmux's behaviour, not Terminaler's binding. The intercept now runs first and consumes the event, with its release swallowed so no application sees half a click, making ctrl+right-click terminaler-owned everywhere. Also dropped `flip-split` from the grid's name table: it listed 10 names for a 3x3 grid, so index 9 was unreachable and its handler branch dead — it remains on the 10-button toast, which does have a cell for it.
- **The sidebar dock chips flashed continuously, and the cause was the config watcher.** Terminaler watches the config file's *parent directory* so that swapping a symlink is noticed, but the watcher thread collected event paths and never compared them to anything — so **any** file event in `~/.config/terminaler/` forced a full `reload()`. That directory is not quiet: session state, `web-status`, editor backups and stray files all land there. A reload is not cheap; it drops every font cache, and a fresh `LoadedFont` starts with an empty `tried_glyphs`, so every glyph needing font fallback re-resolved and re-shaped. The chips fell back to the base font and re-converged through two async fallback rounds, changing width each time — the ASCII `+` chip never moved, because it never needed fallback. Reproduced by touching an unrelated file in the config directory five times: 6 reloads, chips jumping between 29.3px and 43.6px on every touch. After the fix the same test gives 0 reloads and the chips hold their settled widths, while touching the real config file three times still gives exactly 3 reloads — the filter is precise, not blunt. A poisoned lock falls through to reloading, since a missed reload looks like the config being ignored. Also guarded `change_scaling` against no-op calls, which clear every font cache unconditionally and feed the same re-resolve churn; that is a separate genuine defect found along the way and was **not** what caused the flashing (in a clean run it is called zero times). Three confident diagnoses were wrong before the trace settled it — the `insert_fallback_handles` → `ClearShapeCache` loop (disproved: `revised fallback` logged 0 times), `change_scaling` as the driver (its 52 calls were themselves downstream of the reload storm), and "pre-existing, not my change" (stated before the comparison was valid). Two method notes worth keeping: debug logs were being written into a watched directory and were themselves amplifying the storm roughly 30x, and `sort | uniq -c` on the probe frames hid the answer by destroying their order — printed in time order, the three states were plainly convergence over 272ms, not steady-state oscillation, which reframed the question from "what oscillates?" to "what keeps resetting it?".
- **Panes inherited `TMUX` from whatever session launched the app, so `tmux new-session` inside one silently became a window somewhere else.** Reported as "split a pane, type `tc`, and nothing happens — or the tmux session is created somewhere else". Both halves are one mechanism. A spawned pane's environment is a snapshot of the *spawning process*'s environment (`CommandBuilder::get_base_env`, `pty/src/cmdbuilder.rs:74`, over `std::env::vars_os()`) — not, as it first appears, of the parent pane's shell. Launch the GUI from inside a tmux session and every pane it spawns therefore has `TMUX` and `TMUX_PANE` set, pointing at that outer session. Any tmux-aware tool then acts on it: the user's `tc` script branches on exactly this (`[ -z "${TMUX:-}" ]`), so instead of `tmux new-session -A` it ran `tmux new-window` against the launching session — which created the window, ran the command, and left it in a session the user was not looking at. Nothing appeared in the pane, and the work turned up elsewhere. The scrub list `mux_env_remove` already existed for precisely this class of leak but covered only `SSH_AUTH_SOCK`/`SSH_CLIENT`/`SSH_CONNECTION`; `TMUX` and `TMUX_PANE` join the default, since a pane claiming membership in a session it is not in is wrong for every user of a terminal multiplexer. The list was also applied in **one** process only — `terminaler-mux-server` at startup (`main.rs:199`) — while the GUI constructs its own in-process `LocalDomain` (`terminaler-gui/src/main.rs:629`) and had no scrub at all, so the config key was a no-op for exactly the topology that hits this bug. `build_initial_mux` now applies the same list before creating that domain. Verified headlessly on Linux by launching the mux server from inside a live tmux session and reading the env of a pane it spawned: after the fix both variables are `unset`, and `tc`'s own branch test resolves to the visible `new-session` path. That measurement covers the **daemon** path only, via a server-built default-prog spawn. The pre-fix leak on that same path is *inferred* from the code rather than observed — the old default list lacked `TMUX` and the server's exec-time environment carried it — because the one "before" run used the client-PDU spawn described below, which is not the same path. The **GUI** path (its in-process `LocalDomain`, the topology that produced the report) was later confirmed live on the affected Fedora/Wayland box, and the pre-fix leak observed rather than inferred: the old GUI there had been launched from `terminaler:9` and carried `TMUX`/`TMUX_PANE` in its environment. The confirming test needs the bug condition deliberately reintroduced — a pane of a GUI launched *without* `TMUX` proves nothing, since there was nothing to scrub. Launch a throwaway GUI with `TMUX` and `TMUX_PANE` set, confirm them present at exec, then read the environment of a pane it spawns: both absent, with `TERM` and `TERMINALER_PANE` still visible to show the read itself works. Note a running GUI keeps both its old binary and its old environment, so a full restart is required; and `terminaler cli list`/`spawn` do reach the GUI's in-process mux, so this path is drivable from the CLI. Worth knowing for anyone testing this: `terminaler cli spawn -- <prog>` cannot reproduce it, because the **client** builds the `CommandBuilder` and the PDU ships its serialized env map to the server (`codec/src/lib.rs:678`), so the client's own `TMUX` arrives downstream of the server's scrub. Spawn with no command — letting the server build the default prog — or the test measures the wrong process. Two false starts preceded the working check. `cargo build --bin terminaler-gui` leaves the mux-server binary stale, so rebuild each binary whose behaviour you intend to test — but **do not verify that with `strings`**: it has no discriminating power here. Rust packs `&str` literals into a shared constant blob with suffix overlap, so the bytes appear as `TMUX` and a truncated neighbour rather than a matchable `TMUX_PANE`, and an anchored grep returns 0 on a binary that definitely contains the list. The control that settles it is `SSH_AUTH_SOCK`, which has been in `default_mux_env_remove()` far longer than this fix and which `strings` also reports as absent — a check that cannot see a known-present string cannot prove a new one missing. Grep the rlib (`target/*/deps/libconfig-*.rlib`) instead, or just trust cargo's up-to-date check. And `/proc/<pid>/environ` is the exec-time snapshot, so it still shows variables a live process has since removed and cannot confirm a `remove_var` — though it *is* valid evidence for a binary whose code never removed them.

### Changed
- **The sidebar has one renderer again: the GPU tile rail, on both platforms.** The sidebar shipped two independent implementations — GPU box-model elements in `tab_sidebar.rs` on Linux, and a WebView2 child window rendering `assets/sidebar.html` on Windows. They shared no code, so the HTML was a spec the Rust side tracked by hand, and the drift was the source of a run of bugs the changelog already records: `--bg-hover` referenced but never defined (resolving one way for the inherited `color` and another for `background`), a second differently-encoded copy of the status palette in the flyout, and row fills that matched on one platform only. Consolidating on WebView2 was not available: WebView2 is a Windows API, `wry` sits under `[target.'cfg(windows)'.dependencies]`, and its Linux backend needs webkit2gtk/GTK embedding that the `window` crate — raw `wayland-client` and `xcb` — has no dependency on. So Windows moves to the rail Linux already runs. Removed: `webview_sidebar.rs`, `assets/sidebar.html`, `ci/webview-sidebar-check.sh`, the `set_flyout` IPC and its host-widening path, `serialize_sidebar_state`, `handle_sidebar_ipc`, `compute_sidebar_geometry`, `claude_to_json`, the `WM_APP+100` deferred-`SetFocus` glue, the `wry` dependency (689 lines of transitive lockfile), and `WebView2Loader.dll` — which was shipped **only** for the sidebar, so the Windows support-file set drops from three files to two (`conpty.dll`, `OpenConsole.exe`). `assets/mockups/` stays: it is design history for the rail that survives. Two documented trade-offs retire with the WebView: the widened host covering the resize-handle strip while a drawer was open, and the flyout opening a paint late on an idle window. Verified by `cargo check` on both the Linux host and the `x86_64-pc-windows-gnu` target (zero errors on each) — the Windows target matters most here, since every deleted line was `#[cfg(windows)]`.

### Changed
- **The sidebar's sync and theme controls moved to a single icon row pinned to the bottom.** `sync`, `+` and `theme` had been split across a full-width row and a two-chip dock partway up the rail; they are now one row of icon buttons — `+` leading as the primary action on a filled chip, then `⇄` (sync) and `◑` (theme) as dimmer utilities — pinned to the sidebar's bottom edge. Pinning is by measurement: the tabs container and agents section are probed with `compute_element` and the leftover slack becomes the row's top margin, with a `max(DOCK_TOP_MARGIN)` floor so a short window degrades to ordinary document flow instead of overlapping the sections above. That floor matters — the earlier attempt at a bottom-pinned dock stretched a child against a *predicted* height the layout was free to exceed, which pushed it off-screen. Sync rejoins the dock only because single glyphs fit where three *text* chips once overflowed and clipped the last one, and it still appears only when tmux discovery is configured, so the button is never dead. Glyph choice is the standing risk here — an absent glyph rasterizes to nothing and leaves a silently dead button, which is how two refresh glyphs died during the original rail work — so all three were checked with `ls-fonts` to resolve to real glyph ids rather than `.notdef`.

### Fixed
- **A hover highlight could lag the pointer by a whole element.** Moving left to right along the dock, a chip did not light up until the pointer reached its far edge; right to left looked correct. Two rounding conventions were in play for the same rectangle: `ui_item_impl` registers hit rects as **integers**, truncating `min_x` and `width`, while the paint-time hover test in `render_element` compared the pointer against the raw **float** `bounds`. On the pixels between the truncated edge and the true edge the two disagreed. Measured on a live window, sync's hit rect was `1610..1653` against float bounds of `1610.5..1654.1`: at x=1610 hit-testing resolved to sync and fired its one invalidate, but the repaint still evaluated `1610 >= 1610.5` as false and drew the *previous* chip as hovered — and because invalidation only happens when the resolved item changes, nothing repainted again until the next boundary at 1654. Right-to-left crossings land on the other side of that same edge, which is why only one direction looked broken. The hover test now derives its rect exactly as `ui_item_impl` does, so the two agree on every pixel by construction (the old test disagreed on 2 pixels per boundary; the new one on none). This is a shared box-model path, so every hover-styled element benefits — the dock chips are simply where adjacent narrow targets made it visible. Ruled out by measurement rather than reasoning: the hit rects themselves (transitions land exactly on their edges, symmetric in both directions), `resolve_ui_item`'s reverse scan (a single candidate at every sampled point), and the Wayland stale-frame-callback path (its warning never fired). Three arithmetic models of the chip geometry preceded the instrumented run and were all wrong, each resting on an assumed glyph advance that `ls-fonts` had already contradicted.

- **A copied selection is now offered to every window, not just the active one.** Ports upstream WezTerm `40daec8` (#7863, fixes #6685). Wayland delivers the copy-selection event once per *client*, but the handler stored the offer in a single `CopyAndPaste` — the one belonging to whichever surface was active when the clipboard changed. Any other window had no offer to read, so pasting into it silently did nothing. The offer now goes to every window in `surface_to_pending`, each holding a clone of the same underlying `WlDataOffer`. `resolve_copy_and_paste` had no other caller and goes with it; unlike upstream its `impl WaylandState` block stays, because this fork added `lock_pointer_state` to it. Verified live on Wayland — two clipboard changes against a running GUI, no panic or deadlock in the broadcast loop, clipboard chain intact. The remaining behaviour (paste into a window that was inactive at copy time) needs two windows and a hand on the mouse, so it is left as a manual check.
- **The second upstream Wayland fix of that pair needed no port.** `5f06945` (skip data-device events for non-toplevel surfaces, refs #7880) is already covered: `daf82ca` independently made the same change, resolving the offer's surface with the fallible `try_from_wl`, and goes further by destroying the orphaned offer — which upstream does not. One deliberate divergence stands: upstream resolves `window_id` *before* calling `accept_mime_type`, so it never accepts a mime type on a foreign surface's offer, while this fork accepts, then bails and destroys. Harmless, since the destroy supersedes it, and reordering would churn a path already hardened past upstream. With this pair settled, no known upstream Wayland fix is outstanding.
- **Wayland buffer dimensions are aligned to the integer scale factor.** Ports upstream WezTerm `6ff5492` (#7746), which this fork never received. The Wayland protocol requires buffer dimensions to be an integer multiple of `buffer_scale`; without the alignment a fractional-scaling compositor can reject the buffer with a protocol error and take the window down. Applied at both upstream sites — `WlEglSurface` creation and the configure handler after the `resize_increments` adjustment — by hand rather than by cherry-pick, because the configure site sits below this fork's `subtract_borders` block, which upstream does not have. Checked in the same pass: the five recent Wayland hardening commits (`todo!()` seat handlers, the missing-keymap abort, panicking `from_wl` in the frame callback, the window-map `expect`, and the resize shrink) are **not** fixed upstream — `upstream/main` still carries every one of those panics, and `subtract_borders` appears nowhere in its `window.rs`, so that bug and its fix are fork-local. Those commits are original work, not duplicated effort.


## 2026-08-24

### Fixed
- **The window froze on a stale frame after a monitor slept, and nothing could recover it.** Painting is gated on a pending `wl_surface::frame` callback: `do_paint` stores the callback and dispatches `NeedRepaint`, and while it is set both `invalidate` and `do_paint`'s early return only mark `invalidated` and return, so nothing paints and nothing commits. The single path that clears it is the compositor delivering the callback. Delivery is not guaranteed — mutter dropped one during a monitor reconfiguration (`meta_monitor_manager_get_logical_monitor_from_number` assertions logged at the exact second of the last paint) and never redelivered it. The window then showed the same frame for twelve hours while the process stayed **completely healthy**: main thread idle in `epoll_wait`, 0% CPU, input dispatching, mux answering `cli list`, and PTYs still running injected commands — a render stall that reads as a freeze with no crash and no recovery short of restarting. Resizing and maximizing could not clear it either, because the configure path defers the same way. `do_paint` now stamps when the callback was requested and both deferral points treat one older than a second as lost, dropping it and painting anyway. **Verified in production**: it fired once on Fedora/Wayland (`pending frame callback outlived 1s`), the window repainted and carried on, with no repeat discards — the signal that the callback flow recovered rather than the watchdog masking a persistent stall. The one-second threshold doubles as a repaint throttle for surfaces whose callbacks a compositor legitimately withholds (a hidden window), so the discard warns once per stall episode and logs at `debug` after. A fully idle window still waits for the next `invalidate`, so worst case the first keypress unfreezes it. Diagnosis and patch sent upstream, where `main` still carries the same unguarded code, on [wezterm#5284](https://github.com/wezterm/wezterm/issues/5284) — open since 2024 with the matching "it redraws as soon as I move the mouse over it" symptom across KWin, Hyprland, Nvidia and AMD, and no root cause found in two years.
- **Ten panics in Wayland event handlers, each of which killed every pane.** A panic inside a handler cannot unwind: the dispatch stack crosses libwayland's C frames, so Rust aborts. The GUI died this way from a stray drag (`SIGABRT`, core dumped) — `SurfaceUserData::from_wl` is `wl.data().expect(...)`, and the drag entered a surface carrying no user data, which is normal for the client-side decoration frame's own subsurfaces and for an offer whose surface is already destroyed. An audit of all twenty dispatch entry points found nine more. The worst is `frame_action`, which drove the xdg window through five unwraps while `close` drops that window and leaves the inner in the window map, which nothing ever removes per window — so a decoration click landing between the close button and teardown found the entry and unwrapped `None`. Also: three drag handlers unwrapped `self.pointer`, which is unset until a seat announces pointer capability (a touch- or keyboard-only seat was fatal); the drag enter handler unwrapped a drag offer that is absent when the drag is cancelled between events; both uses of `active_surface_id` unwrapped it although it is `None` until the first Enter, so a Leave, Motion or Axis arriving first aborted; the keyboard handler expected a keymap on every event even though all three keymap-loading failure paths log and leave it unset, turning an XKB layout xkbcommon cannot compile into a dead GUI; both `SeatHandler` methods were bare `todo!()`, which fire on runtime seat hotplug; and the frame callback and window-event handler used the same panicking surface lookup. Every site now resolves fallibly and returns, following `keyboard.rs`'s existing `try_from_wl` precedent. Deliberately left alone: the output-manager and text-input unwraps, whose handlers only receive events when those optional protocols were bound, and mutex locks, which fail only after a prior panic. Worth knowing before anyone audits further — `frame.rs` is commented out of `mod.rs` and not compiled, despite the panicking calls in it.

### Notes
- **`cargo check -p window` is not sufficient to validate Wayland backend changes.** It passed on code that `cargo build --bin terminaler-gui` rejected for a missing `use wayland_client::Proxy;`, because check never exercised the path. Run the full binary build before committing. Separately, `cargo build` can report `Finished` in ~0.3s from cache without having compiled the edit at hand; `touch` the changed files, or confirm with `strings <binary> | grep <new log message>`, before believing a build included them.
## 2026-08-22

### Changed
- **The GPU sidebar is redesigned as a compact tile rail with hover flyouts** (the "V2 Tiles" spec, chosen from three HTML mockups in `terminaler-gui/assets/mockups/`). The 360px card list becomes a rail of bordered tiles — status-tinted borders, in-tile dots and notification counts, a context strip, uppercase group eyebrows, pane sub-tiles, a `+ theme` dock and a `sync` row — with all detail (model, branch, stats, close/mute/attach actions) moved into a flyout that opens after a 200ms hover and overlays the terminal without shifting cells. Tiles anchor to both rail edges, so widening `tab_sidebar_width` widens every tile, and the new `Entity::Sidebar` font in `terminaler-font` scales with the configured width (`font_size × 0.8 × width/180`, clamped 8–16pt). Tmux tiles show the **project** (session name) on the label line with the agent riding the icon line. Colors come from a `SidebarTheme` struct mirroring `sidebar.html`'s `:root` token block — the hand-tracked shared spec. Validated over seven rounds on Fedora/Wayland via an agent-driven loop (build provenance checks, portal screenshots over pCloud); the round-trip surfaced and fixed, among others: `update_next_frame_time` armed outside a paint never fires (the flyout never opened — arming now also invalidates); the layout engine ignores `min_width` on a root element (position flyouts by their *painted* width); estimating tile heights from font metrics undercounts (budget the section with probe-*measured* heights or short windows clip mid-tile); glyphs beyond the font's coverage vanish silently (two refresh glyphs died; the dock uses text chips); and three text chips overflow the dock, clipping the third (the sync control became a full-width row in the tmux section). The WebView (Windows) side is restyled to the same spec in the same day's work: `sidebar.html` rebuilt around the tile rail with a `set_flyout` IPC that widens the WebView host over the terminal while a flyout or drawer is open (terminal cell layout derives from `tab_sidebar_width` alone, so cells never shift), icons as CSS-mask SVGs, and headless-chromium verification against `assets/mockups/sidebar-fixture.json` (`ci/webview-sidebar-check.sh` regenerates the harness). The default `tab_sidebar_width` drops 360 → **180** (the rail's reference width) and the drag floor 120 → 100; the drag handle **stays** — responsive tiles and live font scaling reversed the earlier plan to remove it. Known, deliberate gaps until a Windows box exists to verify on: `set_flyout`'s host-widening happens in the parent's paint loop, so an idle terminal may open the flyout a paint late (and until that reposition the flyout area is zero-width); panel translucency (80% on the GPU rail) awaits the WebView2 `with_transparent` spike; and drag-resize does not persist across restarts — width snaps back to config, by design for now.

### Fixed
- **Ten findings from the post-redesign code review.** A phantom sidebar resize could resume after focus loss (drag state now clears with the rest on defocus); a tmux box with zero sessions rendered nothing on the GPU rail for any status — a Pending/Unreachable box was indistinguishable from an unconfigured one (session-less boxes now show their eyebrow and error, and the empty-box check runs before the vacuously-true folded check that was swallowing them); `change_scaling` cleared every font cache except the new rail font, leaving stale-DPI glyphs after a monitor change; the tabs section was unbudgeted, so enough tabs pushed the tmux section and dock off-screen (per-element measurement now folds trailing tiles into a "+N more" row); the tab flyout's close chip bypassed the flyout-clearing press path and the flyout silently re-anchored to the shifted next tab; the flyout detail carried its own differently-encoded copy of the status palette (now the same `status_color`/theme mapping as the rail); the WebView IPC queue drains only during a parent paint, so a flyout close on an idle window left the widened host as a dark column until something painted (message arrival now invalidates the parent); JS tile clicks neither cancelled the armed hover timer nor closed an open flyout (both now mirror the GPU close-on-press); and two more Wayland content-vs-window-size sites — the synthetic configure in `set_inner_size` got the titlebar subtracted twice, and creation-time `set_window_geometry` reported frameless geometry. One finding is a documented trade-off rather than a change: while a click-drawer is open, the widened WebView host covers the resize-handle strip, so a drag attempt dismisses the drawer first.
- **Wayland window shrank by one titlebar on every resize motion.** Dragging any resize edge under a client-side frame made the window lose height per mouse-move until it collapsed. The configure handler subtracts the frame borders from the configured size to get the content area, then reported *that reduced figure* to the compositor via `set_window_geometry` — but geometry describes the whole window, so the compositor was told the window was one titlebar shorter than it is, its next configure came back that much smaller, and the titlebar came off again, compounding per event. Now adds the borders back before reporting. Only the **height** was affected because `sctk-adwaita`'s `subtract_borders` returns the width unchanged, which is exactly why the window narrowed correctly but lost height, on both left and right edges. Applies only to the client-side frame; GNOME's Mutter declines server-side decorations, so it is the path GNOME always takes.
- **A newly configured tmux box never appeared in the sidebar.** `paint_tab_sidebar` caches the built element tree and rebuilds only when a fingerprint of the discovery snapshot moves, but the fingerprint iterated `snap.sessions` **only** — so a box whose probe had not answered yet contributed nothing, and *"box present but empty" hashed identically to "box absent"*. A box added to the config stayed invisible until something unrelated happened to invalidate the cache, which is indistinguishable from a failed SSH probe. The fingerprint now includes each box's name and status. Status matters on its own: it drives the header dot and the error line, neither of which is a session. Two things that look decisive here and are **not**: `ps --ppid` sampling misses a sub-second probe, and zero `tmux discovery` lines in a debug log is what *success* looks like, since every one of those `log::debug!` calls sits in an error arm.
- **Agent badge painted over the session row's right border and rounded corner.** The badge is `Float::Right`, and `box_model` positions such a child with `float_max_x = (max_x + float_width).min(max_width)` where `max_width` falls back to the **parent's** full bounds when the element sets none. The row set none, so the badge was clamped to the sidebar's edge rather than the card's. Setting `max_width` on the row fixes it. Neither shortening the name text nor shrinking the row's `min_width` moves a floated child — measured, the latter shifted the card 10px left and left the badge at the identical x. Verified by pixel scan: badged and unbadged rows now end at the same x.

### Changed
- **Linux sidebar's tmux section now matches the Windows WebView.** The two are separate renderers — Windows draws HTML in a WebView2 from `terminaler-gui/assets/sidebar.html`, Linux builds GPU box-model elements in `tab_sidebar.rs` — so nothing is shared and the CSS is a spec the Rust side has to track by hand. Added the missing `TMUX SESSIONS` heading (mirroring `.stats-title`: 10px, weight 700, uppercase, `--accent-orange`), and stopped filling the session rows. `.tmux-session-row` asks for `var(--bg-hover)`, which `:root` never defines, so on Windows it resolves to transparent — sampling inside a row in a reference screenshot gives `#1a1a1a`, the same value as the gap between rows, while the GPU rows filled with `border_subtle` and read as solid blocks. Hover still lifts the fill. Verified against a Windows screenshot: row interior, badge fill, status dot and text colours all match, at the same 41px row pitch.

## 2026-08-07

### Fixed
- **Tmux instance badge was unreadable white-on-yellow**: `.tmux-session-agent-instance` set `color: var(--bg-hover)`, a custom property that is **never defined anywhere** in `sidebar.html`. Because `color` is an inherited property, an invalid `var()` resolves to the inherited value rather than the initial one — so the badge took the row's near-white `--text-primary` (`#e0e0e0`) on the orange `--accent-orange` (`#db8b0b`) background: a contrast ratio of **2.06:1**, well below the 4.5:1 accessibility floor. Now uses `--bg-base`, giving **6.88:1**. Two sibling symptoms of the same missing variable remain and are cosmetic only: `.tmux-session-row`'s `background: var(--bg-hover)` silently resolves to transparent (`background` is *not* inherited, so it falls to the initial value), and `--bg-tertiary` is likewise referenced but never defined.

### Added
- **`ci/build-windows-staging.sh` — cross-build for Windows without quitting Terminaler.** `~/pCloudDrive/terminaler-windows-build/` **is** the folder the Windows exes run from, not a staging area, so building into it *was* deploying — and since Windows locks running exes, every build required closing the app first. Builds now land in the sibling `terminaler-windows-staging/`, which syncs harmlessly while Terminaler runs; `--promote` then copies staging → live behind a timestamped backup of the current exes, and is the only step needing the app (and `terminaler-mux-server.exe`) closed. Also `--status` (compare staged vs live mtimes) and `--dry-run`. Ships the full 6-file set — 3 exes plus `WebView2Loader.dll`, `conpty.dll`, `OpenConsole.exe` — and writes a `BUILD-INFO.txt` recording commit, branch, dirty-state and sha256, so a build's provenance is never in doubt again.

### Changed
- **`CLAUDE.md` config documentation corrected — it was substantially wrong.** It stated "Config keys: camelCase in JSON" and documented `profiles`, `layouts`, `workspaces` and `keybindings` sections; **none of those keys exist in the parser** (`grep -rn "profiles" config/src/*.rs` returns nothing). The JSON keys are the literal **snake_case** Rust field names — the `Config` struct derives `FromDynamic` with no rename attributes — e.g. `default_prog`, `default_domain`, `font_size`, `web_access`/`bind_address`, and `keys` (not `keybindings`). `config/src/defaults.rs` is the accurate reference. This also resolves a self-contradiction: the 2026-08-06 entry above (and the `tmux` section note) claimed the `tmux` section used snake_case "unlike most of the config" — in fact the *whole* config always has.

### Notes
- **`default_prog` does not apply to WSL panes, and this fork defaults to WSL.** `terminaler-gui/src/main.rs:585-595` prefers the first WSL domain as the default (falling back to `local` only when no distro exists), and `mux/src/domain.rs:438-441` reads `default_prog` from *that domain* — which `WslDomain::default_domains()` leaves unset — via `.map(…).unwrap_or(…)`, a chain that yields `Some(None)` and therefore silently discards the top-level value. This is **upstream WezTerm behavior** (it arrived verbatim in the `f425086` snapshot), i.e. deliberate namespace separation, not a bug: top-level `default_prog` is a local-domain concept and WSL domains carry their own. To point new panes at a remote host, pair the two settings — `"default_domain": "local"` alongside `"default_prog": ["ssh", "<host>"]` — so ssh runs as a Windows process with the Windows ssh config. Making `default_prog` fall through to WSL panes would *not* be equivalent: `fixup_command` wraps a WSL domain's command as `wsl.exe --distribution <d> --exec <args>`, so it would run ssh from *inside* WSL with WSL's ssh config.
